# 实验室资料库与项目资料权限需求

## 背景

OpenColab 当前以项目为主要工作空间。科研人员会在项目中上传论文、表格、PDF、实验数据，也会通过任务、Agent、LLM 对话生成分析结果、研究假设、实验设计、报告草稿和研究记忆。

如果所有资料只留在项目或会话中，长期会出现几个问题：

- 同一篇文献会被不同项目重复上传、解析和向量化。
- 项目结束后，有价值的资料和研究产物不容易被新项目复用。
- 实验室成员很难系统性阅读、检索和引用已有资料。
- 如果简单做成“全局知识库自动汇总所有项目资料”，又会破坏项目数据权限和科研隐私。

因此需要引入一个受权限控制的实验室资料库，把“资料资产沉淀”和“项目权限隔离”同时做好。

## 目标

建立一个统一的资料资产层，使 OpenColab 支持：

- 上传文档、项目生成文档、LLM 对话沉淀文档的统一管理。
- 项目资料默认只在项目内可见。
- 只有被明确发布的资料才进入实验室层级资料库。
- 新项目可以从实验室资料库引用公开资料。
- Agent 和任务运行时可以基于项目上下文读取项目已引用的资料。
- 研究记忆既能服务当前项目，也能在授权后沉淀为实验室可复用资产。

一句话原则：

> 进入实验室资料库不是存储动作，而是发布动作。

## 范围

资料库管理的资产不限于用户上传文件，也包括系统运行过程中生成的资料。

### 资料类型

- 上传文件：PDF、Word、表格、数据文件、图片、压缩包中的文档。
- 外部引用：URL、DOI、公开论文元数据、网页快照。
- PI/Admin 直接导入的实验室资料：实验室公共文献、共享数据、SOP、课程材料、历史资料。
- 项目生成文档：任务报告、文献综述、实验设计、分析报告。
- 研究记忆：讨论、假设、证据、结论、研究对象关系。
- LLM 对话沉淀：用户主动保存的摘要、笔记、草稿、结论。
- 实验资料：SOP、protocol、实验记录、实验数据说明。

## 核心概念

### 资料资产

资料资产是系统中所有可阅读、可检索、可引用、可权限控制的内容单元。

建议概念名：

```text
Asset
```

或更具体：

```text
ResearchAsset
```

每个资产至少需要记录：

- `id`
- `type`
- `title`
- `description`
- `content_ref`
- `owner_id`
- `origin_project_id`
- `origin_session_id`
- `visibility`
- `processing_state`
- `metadata`
- `created_at`
- `updated_at`

其中 `type` 可包含：

```text
uploaded_file
generated_doc
research_memory
report
dataset
protocol
external_reference
```

### 可见性

资料默认不公开。推荐使用显式 `visibility_scope` 表达资料可见范围：

```text
private
project
lab_private
lab_public
```

含义：

- `private`：仅 owner 可见。
- `project`：项目成员可见。
- `lab_private`：实验室范围私密资料，PI/Admin 可见和管理，普通实验室成员默认不可见，除非被项目明确引用。
- `lab_public`：实验室成员可见，可在实验室资料库中检索和引用。

项目中上传或生成的资料默认应为 `project`，除非用户明确选择私有。

实验室成员边界不等同于系统内所有用户。用户需要先注册或被创建为系统用户，再由项目管理员、PI 或 Admin 添加到具体项目或实验室范围。只有属于实验室成员集合的用户，才能看到实验室层级资料库中的可见资料。

### 资料合集 / Collection

当前阶段不引入完整的研究组/Team 人员体系。`group` 在产品上应理解为资料合集，用来整理资料，不用来授权。

这里需要明确区分资料合集和权限：

- 资料合集只是“把资料放在一起方便整理”，推荐命名为 `AssetCollection`，产品文案可以叫“合集”。
- 项目成员可以把自己权限范围内的资料整理为项目合集。
- 合集不改变资料本身的权限；用户能否看到合集里的某个资料，仍由该资料自己的 `visibility_scope` 和项目引用关系决定。
- 把资料加入合集不等于把资料授权给其他人。
- 如果一个用户能看到合集，但无权访问合集里的某个资料，该资料应被隐藏或显示为“无权限资料”占位。
- 未来如果确实需要“某一组人员共同访问一批资料”，再引入轻量 `shared_collection` 或完整 `ResearchTeam`。

### 研究组 / Team（未来可选）

研究组是人员和权限边界，不是资料文件夹。当前阶段暂不实现，以免过早引入人员组织、角色和跨项目权限管理。

未来如果要做，可以使用以下概念名：

建议概念名：

```text
ResearchTeam
```

或产品文案：

```text
研究组 / 课题组 / Team
```

研究组位于实验室和项目之间：

```text
Lab
  > ResearchTeam
      > Project
```

它解决的是“实验室内一部分成员共享一批资料”的问题。只有当简单的项目权限、实验室公开/私密权限和资料合集不足以表达真实协作关系时，才应引入。

研究组最小字段：

- `id`
- `name`
- `description`
- `lab_id`
- `created_by`
- `created_at`

研究组成员关系：

```text
ResearchTeamMember
```

- `team_id`
- `user_id`
- `role`: `owner | member`
- `created_at`

研究组和项目关系：

```text
ResearchTeamProject
```

- `team_id`
- `project_id`
- `created_at`

说明：

- 一个项目可以不属于任何研究组。
- 一个项目 v1 可以先只属于一个研究组；v2 再考虑多研究组。
- 研究组成员不等于项目成员；项目成员仍需单独添加。
- PI/Admin 可以查看和管理所有研究组资料。

### 项目引用

项目引用资料不等于公开资料。

一个公开资料可以被多个项目引用；一个项目私有资料也可以只属于当前项目。

建议概念名：

```text
ProjectAssetLink
```

字段：

- `project_id`
- `asset_id`
- `link_type`
- `created_by`
- `created_at`

`link_type` 可包含：

```text
source
output
memory
reference
```

### 权限

建议使用显式权限记录承载后续扩展：

```text
AssetPermission
```

字段：

- `asset_id`
- `subject_type`: `user | project | lab`
- `subject_id`
- `permission`: `read | write | manage`

v1 可以先不完全实现复杂 ACL，但数据模型应为后续扩展保留空间。未来如果引入 `ResearchTeam`，再扩展 `subject_type = team`。

## 权限规则

### 默认规则

- 用户上传到个人资料库的资料，默认 `private`。
- 用户在项目中上传的资料，默认 `project`。
- 任务、Agent、LLM 对话在项目中生成的资料，默认 `project`。
- 保存到研究记忆的内容，默认继承当前项目权限。
- 资料不会因为被存入系统而自动进入实验室资料库。

### 发布规则

只有明确执行“发布到资料库”的动作后，资料才会从项目上下文进入更高层级的共享范围。发布目标必须明确选择为 `lab_private` 或 `lab_public`，不能再使用笼统的 `lab` 可见性。

允许发布的人：

- 资料 owner。
- 项目 owner。
- PI。
- Admin。

项目 owner 发布资料时，可以选择发布为实验室范围私密资料或实验室范围公开资料，不需要 PI 审核。

实验室范围私密资料可被 PI 查看和管理，但不会对普通实验室成员公开。

PI 可以查看实验室范围内的资料，包括项目发布出来的资料、已公开资料，以及实验室范围的私密资料。PI 也可以修改资料的公开/私密属性。

实验室资料也可以由 PI 或 Admin 直接上传、导入或创建，不需要先来自某个项目。直接导入的实验室资料应记录导入人、导入时间、资料来源说明和初始可见性。

如果资料来自项目，发布动作应记录：

- 发布人。
- 来源项目。
- 发布时间。
- 发布说明。
- 发布可见性。

### 撤回规则

资料被撤回实验室公开后：

- 不应删除原始资产。
- 不应删除项目内引用。
- 不应影响已经存在的项目引用。
- 应取消后续新的实验室公开发现和引用入口。
- 已经引用该资料的项目继续保留引用，但需要在引用方提示“原资料已撤回公开”。
- 后续访问仍需根据项目引用关系和当前权限判断。

### 合集规则

合集不是对资料授权，而是对资料进行整理和组织。

适用场景：

- 项目成员把项目资料整理成“背景文献”“实验数据”“待复核资料”等合集。
- PI/Admin 把实验室公开资料整理成推荐阅读合集。
- 用户把自己有权访问的资料整理成个人工作合集。

关键规则：

- 项目成员可以创建和编辑项目合集。
- 项目成员只能把自己有权访问的资料加入合集。
- 合集内资料仍按原始资料权限判断访问。
- 合集不能让无权限用户绕过资料权限。
- 删除合集不删除资料资产本身。
- 从合集移除资料只移除组织关系，不撤回资料的项目引用或实验室发布状态。

### 项目引用规则

项目可以引用实验室公开资料，也可以在 PI/Admin 授权时引用实验室私密资料。

引用后：

- 资料进入该项目的上下文。
- 项目成员可以在项目内阅读和使用。
- Agent 和任务可以把它作为项目资料参与检索。
- 不改变该资料本身的 owner 和原始来源。

公开资料被项目引用后，即使后续撤回公开，也不影响既有项目引用。系统应保留引用记录和可追溯来源，并向引用项目提示资料的公开状态已经变化。

### 研究记忆发布规则

研究记忆发布到实验室资料库后不可编辑。

如需修订，应创建新的研究记忆版本或新的资料资产，并保留原始发布记录。

### 统一权限模型规则

数据文件和论文 PDF 使用同一套资产权限模型。

不同资料类型可以拥有不同的预览、解析、向量化和下载能力，但可见性、引用、发布、撤回和审计规则应保持一致。

## 用户体验需求

### 资料库页面

面向所有有权限的实验室成员。产品上不应再用“数据源 + 分组”作为核心心智，而应使用“资料库 + 可见范围”。

需要支持：

- 浏览个人资料、项目资料、实验室资料和资料合集。
- PI/Admin 直接上传或导入实验室资料。
- PI/Admin 设置实验室资料为公开或私密。
- 项目成员在项目内创建和维护资料合集。
- 搜索标题、作者、标签、摘要、全文片段。
- 按类型筛选：论文、数据、报告、研究记忆、SOP。
- 按可见范围筛选：我的私有、项目、实验室私密、实验室公开。
- 按合集筛选资料。
- 查看资料详情。
- 引用资料到项目。
- 查看资料来源项目和发布信息。

普通用户只能看到自己有权限的资料：

- 自己的 `private` 资料。
- 自己所在项目的 `project` 资料。
- 实验室成员可见的 `lab_public` 资料。

PI/Admin 可看到更多管理入口。

### 项目资料页面

项目下应有明确的“资料”或“项目资料”入口。

需要支持：

- 上传新资料到项目。
- 从实验室资料库引用资料。
- 查看项目当前已引用资料。
- 查看由任务或对话生成的项目资料。
- 将项目资料发布到实验室资料库。
- 将资料从当前项目移除引用。

### 会话与任务中的资料使用

用户在项目中与 LLM 对话或运行任务时：

- 默认使用当前项目已引用资料作为上下文。
- 可以临时选择会话级资料。
- 会话级临时选择不应自动改变项目资料范围。
- 任务输出可以保存为项目资料或研究记忆。
- 任务输出发布到实验室资料库必须是显式动作。

### 生成文档沉淀

LLM 或任务生成的内容应允许保存为资料资产。

保存入口包括：

- 保存为研究记忆。
- 保存为项目报告。
- 保存为实验设计。
- 保存为文献综述。
- 保存为草稿文档。

保存后默认进入项目资料，项目成员可见。

## Agent 与 RAG 行为

Agent 不应该默认检索整个实验室资料库。

推荐上下文优先级：

```text
当前会话临时选择资料
  > 当前项目已引用资料
  > 当前项目研究记忆
  > 用户明确请求的实验室公开资料
```

关键规则：

- 项目任务默认只读取项目资料。
- 研究组和实验室资料库只在用户明确引用或搜索时参与。
- 未公开项目资料不能被其他项目 Agent 检索。
- RAG 检索结果必须保留 `asset_id`、来源项目、权限来源和引用证据。

## 与现有模块关系

### Source

现有 `Source` 可以演进为资料资产的一种类型，或作为 `Asset` 的底层文件实体。

短期可以保留 `Source`，增加更清晰的权限和项目引用语义。

### Source Group / Collection

现有 `Source.type = "group"` 可以保留为资料合集的兼容实现，但不应作为权限概念强化。

它不承担权限。一个 source group / collection 里的资料是否可见，仍由每个资料自己的 `visibility_scope`、项目引用关系和 `AssetPermission` 决定，而不是由 group 决定。

原因：

- 它是资料合集/文件夹，不是人员权限边界。
- 它不能表达 `private / project / lab_private / lab_public` 这类可见范围。
- 它会让用户误以为“分组”决定谁能看资料。

后续处理建议：

- v1 可以继续使用 source group 承载“资料合集”。
- 产品文案改为“合集”，避免叫“权限组”或“研究组”。
- 项目成员可以把权限范围内的资料整理为项目合集。
- 合集只作为视图组织，不参与权限判断。
- 现有 source group 可以迁移为 `collection`，或作为 collection 的兼容层。

### Research Memory

Research Memory 不应只是会话结果列表，而应成为可被权限控制、可被引用、可被检索的资料资产类型。

### Project

项目是资料使用上下文，而不是唯一存储位置。

项目应维护自己的资料引用集合。

### Session

会话是临时工作现场。

会话资料可以来自：

- 项目资料。
- 用户临时上传。
- 用户临时选择的资料合集或实验室公开资料。

## MVP 建议

### v1：统一项目资料视图

- 把项目中上传的文件、任务输出、保存的研究记忆统一展示为项目资料。
- 项目资料默认只项目成员可见。
- 支持从项目资料中选择内容作为任务上下文。
- 支持把任务输出保存为项目资料。
- 将现有数据源页面中的 `source group` 改造成“资料合集”，不要把它作为权限概念展示。

### v1.5：实验室资料库发布

- 增加实验室资料库页面。
- 支持把项目资料发布为 `lab_private` 或 `lab_public`。
- 支持 PI/Admin 直接上传、导入或创建实验室资料。
- 支持从实验室资料库引用资料到项目。
- 增加发布、撤回、引用记录。

### v2：统一资产权限模型

- 引入 `AssetPermission`。
- 支持更细粒度的 read/write/manage。
- 支持 PI 管理实验室范围资料的公开/私密属性。
- 支持资料版本、引用链和审计。

### v3：知识图谱与跨项目复用

- 将公开资料、项目研究记忆、证据关系纳入图谱。
- 支持跨项目发现相关资料。
- 支持基于实验室资料库生成选题、综述、假设和实验设计。

## 非目标

第一阶段不做：

- 自动公开所有项目资料。
- 默认跨项目检索私有资料。
- 默认把资料合集里的所有资料注入项目任务上下文。
- 复杂企业级 ACL。
- 外部公网资料自动同步。
- 多实验室、多组织租户隔离。

第一阶段应优先保证：

- 默认不泄露。
- 项目内可用。
- 显式发布。
- 可引用复用。
- 可审计追踪。

## 已确认决策

- 实验室成员边界不等同于系统内所有用户；用户需要注册或被创建后，再被加入项目或实验室范围。
- 项目管理员负责把用户添加到项目。
- PI 可以查看实验室范围资料，包括项目发布资料、公开资料和实验室范围私密资料。
- PI 可以修改资料的公开/私密属性。
- PI/Admin 可以直接上传、导入或创建实验室资料，不需要先从项目发布。
- 项目 owner 发布资料时，可以选择发布为实验室范围私密或公开，不需要 PI 审核。
- 研究记忆发布后不可编辑；修订应通过新版本或新资产完成。
- 公开资料撤回公开后，不影响已经存在的项目引用，但引用方需要看到状态提示。
- 数据文件和论文 PDF 使用同一套资产权限模型。
- 当前阶段不引入完整 Team；人员权限先依赖项目成员、PI/Admin 和实验室成员边界。

## 产品原则

- 默认私密，显式共享。
- 资料沉淀和资料公开是两个动作。
- 项目是研究上下文，实验室资料库是可复用资产池。
- Agent 只读取当前权限允许的资料。
- 每一次公开、引用、撤回都应可追踪。
