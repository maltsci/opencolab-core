# Lab Knowledge OS v1 产品需求文档

- 日期：2026-08-07
- 状态：已批准（2026-08-09）
- 产品范围：单一部署实例对应一个实验室
- 交付策略：共同知识基础优先，按纵向切片分阶段交付
- 目标规模：20–100 名活跃成员、最多 200 个正式研究方向、最多 50,000 项资源

## Problem Statement

实验室知识目前分散在成员个人经验、项目过程、文件目录和口头沟通中。成员难以快速回答以下基础问题：实验室有哪些人正在研究某个方向，某个方向经历了怎样的演化，已有成果和公共资源在哪里，资源由谁维护，以及遇到具体问题应向谁咨询。

OpenColab 已具备账号与课题组、项目空间、研究资产治理、项目级检索问答、引用追踪和部分研究对象关系能力，但这些能力仍以项目、会话和资料为中心。系统尚未建立稳定的实验室级 People、Research 和 Resources 实体，也没有让浏览与问答共享同一套知识关系。

如果直接增加四组独立页面，会形成新的信息孤岛；如果先建设通用知识图谱平台，则会引入超出首版需要的数据建模、图数据库和治理复杂度。因此，本版本需要在复用现有系统的基础上，建立小而稳定的实验室知识实体层，并通过人工治理、内部活动聚合和受控 AI 建议持续维护知识质量。

这是下一版本应优先完成的基础工作，而不是产品方向的切换。现有 Discovery Loop 产物缺少实验室级稳定上下文、责任人和可复用资源关系；在继续增加发现能力之前，系统需要先让研究过程产物能够关联长期研究方向并沉淀到受治理的知识基础中。

## 与 Discovery Loop 的关系

> 本节为 2026-08-09 评审会 Q1 拍板结论，是本版本的范围与架构前提。

- Lab Knowledge OS 不是与 Discovery Loop 并行的第二支柱，而是其**实验室知识基础层**。
- Research Direction 承载长期研究领域与上下文；hypothesis、contradiction、gap 将作为过程型 ResearchObject，不混入方向实体。
- 两者通过显式关系连接。成熟的 ResearchObject 可以发起"关联既有方向"或"建议创建正式方向"，统一进入审核队列。
- v1 只交付关联与建议入口，不扩入新的矛盾挖掘、空白识别、假设生成能力；本周期团队优先完成 Knowledge OS v1，不并行推进新的 Discovery Loop 功能。
- 后续版本集成钩子（roadmap 承诺，非 v1 范围）：假设生成读取方向背景与成员上下文；矛盾与空白条目按方向组织；文献检索按方向过滤。v1 数据模型不得阻碍上述集成——ResearchObject 与 ResearchDirection 的关系类型设计须容纳 hypothesis/contradiction/gap 子类而不改 schema。
- Knowledge OS v1 验收（基准问题集评测通过）即为重新评估 Discovery Loop 集成作为下一版本主题的触发点。

## Solution

Lab Knowledge OS v1 建立实验室统一、可持续演化的知识基础，并提供四个共享同一知识网络的入口：

1. **People**：维护成员科研画像，展示当前与历史研究方向、代表成果、负责资源、近期工作和可咨询主题。
2. **Research**：把正式研究方向建设为长期存在的实验室级实体，组织背景、成员、成果、资源、学习入口、相关方向和最新动态。
3. **Resources**：在现有研究资产治理基础上，统一组织数据、文档、代码、模型权重和 GPU 等共享资源，说明用途、维护人、权限和获取方式。
4. **AI Knowledge Assistant**：通过结构化实体查询与现有 RAG 的混合检索回答问题，提供引用和实体链接，并严格继承用户权限。

本版本采用以下治理原则：

- 一个部署实例对应一个实验室；Research Group 表示实验室内部课题组。
- PostgreSQL 继续作为权威数据源，Qdrant 继续用于资源内容检索；不引入独立图数据库。
- 人工维护权威字段，系统自动聚合内部活动，AI 只生成待审核建议。
- 正式研究方向由 PI/Admin 承担最终治理责任；获委派的 Knowledge Steward 可以在授权范围内治理，普通成员可以提交建议。
- 聚合内容和 Assistant 答案逐条继承来源权限，不因进入画像或知识网络扩大可见范围。
- 所有正式关系和重要事实均保留来源、修改人、审核状态及时间历史。
- 核心浏览和维护能力不依赖 LLM，可在完全离线环境运行。

## Goals and Success Metrics

### 产品目标

- 让实验室成员能够从人、研究方向、资源或自然语言问题中的任意入口开始连续探索。
- 让实验室知识从项目和个人手中沉淀为有负责人、有来源、有权限边界的长期资产。
- 让成员画像和研究方向随内部科研活动持续演化，同时保留人工治理权。
- 在不削弱现有项目隔离和研究资产权限的前提下，提高知识可发现性。

### 首轮验收门槛

- 100% 活跃成员完成账号到 People 的迁移，且迁移前后身份、课题组和项目权限一致。
- 100% 活跃成员具备“完整基础画像”。完整基础画像必须包含姓名、实验室角色、所属课题组、至少一个当前研究方向或明确的“方向待确认”状态，以及画像上次确认时间；简介和可咨询主题允许为空，但必须显示对应空状态。
- 100% 由 PI 确认的正式研究方向具备负责人、方向说明和至少一项关联内容。
- 90% 由 PI 标记为关键公共资源的资源具备用途、维护人、获取方式和研究方向关联。
- 阶段 0 由产品负责人联合 PI 和真实实验室成员收集并冻结 30 个真实问题组成的基准集，覆盖找人、找方向、找资源和交叉探索；在阶段 3 验收完成前只允许补充评分标准，不允许为提高结果而替换问题。
- 至少 90% 的基准问题能够返回相关实体，或明确说明当前知识库没有答案。
- 至少 80% 的事实型答案经 PI 或领域成员评审为正确且来源充分。
- 权限泄露事件为 0；任何可复现的越权检索均阻断发布。
- 现有账号、课题组、项目、研究资产、访问申请和项目问答能力不发生权限或数据回归。

### 上线后采用度指标

- 北极星指标为“周活跃知识用户占活跃实验室成员比例”：用户在一周内完成至少一次有效实体搜索、查看知识详情、阅读资源获取说明或向 Assistant 提出问题，即计为周活跃知识用户；上线第 8 周的四周滚动平均目标不低于 50%。
- 有效知识会话比例不低于 70%。有效知识会话指用户从搜索或 Assistant 进入至少一个实体详情、来源或资源获取说明，或者 Assistant 明确返回有依据的无答案结果。
- 每月完成确认或刷新状态的成员画像、方向和关键资源数量，不低于当前受治理活跃实体总数的 10%。
- 采用度只在本地记录聚合事件、匿名化主体标识和时间，不记录查询正文、答案正文或受限资源内容，不向外部分析服务发送数据。

## Current-State and Feasibility Assessment

| 能力 | 当前基础 | v1 处理方式 | 可行性判断 |
|---|---|---|---|
| 实验室成员与角色 | 已有用户、显示名、系统角色、课题组成员和项目成员 | 扩展科研画像及历史关系 | 高，可直接复用身份与成员体系 |
| People 画像 | 缺少方向历史、成果、负责资源、近期工作和咨询主题 | 新增画像与派生视图 | 中，需要新的治理和聚合规则 |
| 正式研究方向 | 已有项目和临时研究对象，但没有稳定方向实体 | 新增 Research Direction | 中，需要迁移、去重和人工确认 |
| 研究对象关系 | 已有部分研究对象关系与证据 | 不直接充当方向关系；复用证据与审计思路 | 高，但需保持概念边界 |
| 资源目录 | 已有 ResearchAsset、发布、版本、访问申请、项目引用和检索 | 扩展类型字段及维护/获取说明 | 高，是本版本复用度最高的部分 |
| 数据与文档 | 已有上传、解析、权限和 RAG | 保持现有行为并关联方向 | 高 |
| 代码与模型权重 | 可作为资产登记，但缺少专属元数据 | 增加类型专属字段，不做远程同步 | 中 |
| GPU | 缺少基础设施连接和实时状态 | 只做目录、配置、负责人和使用说明 | 高；实时监控和调度本版不可行 |
| AI 问答 | 已有项目级 RAG、引用、追踪和模型网关 | 增加跨实体结构化查询和实体导航 | 中，需要新的检索编排和评测集 |
| 自动画像更新 | 已有部分项目活动记录 | 规则聚合 + AI 建议审核 | 中，需要事件口径和幂等刷新 |
| 外部学术数据 | 当前不依赖外部学术服务 | 本版不引入 | 不符合离线优先目标，暂缓 |

## User Stories

### People

1. 作为实验室成员，我希望浏览所有活跃成员，以便知道实验室里有哪些可以协作的人。
2. 作为实验室成员，我希望按课题组、角色、当前研究方向和可咨询主题筛选成员，以便快速找到合适的人。
3. 作为实验室成员，我希望查看某位成员的当前研究方向，以便理解其近期科研重点。
4. 作为实验室成员，我希望查看某位成员的历史研究方向及时间范围，以便理解其研究演化过程。
5. 作为实验室成员，我希望查看某位成员的代表成果，以便判断其经验与我的问题是否相关。
6. 作为实验室成员，我希望查看某位成员负责维护的资源，以便找到正确的资源联系人。
7. 作为实验室成员，我希望查看某位成员近期公开的工作，以便了解其当前进展。
8. 作为实验室成员，我希望查看某位成员愿意接受咨询的主题，以便减少无效沟通。
9. 作为成员本人，我希望维护自己的简介和可咨询主题，以便保证自我描述准确。
10. 作为成员本人，我希望看到系统提出的画像更新建议及其依据，以便决定是否接受。
11. 作为 PI，我希望维护成员的正式角色、课题组和研究方向关系，以便保持实验室知识一致。
12. 作为 PI，我希望选择成员的代表成果，而不是让系统仅凭活动频率自动判断，以便保证展示质量。
13. 作为离开实验室的成员，我希望个人记录被归档而不是删除，以便实验室保留知识历史。
14. 作为无权访问某项目的成员，我希望在他人画像中看不到该项目的敏感活动，以便项目权限不被画像绕过。

### Research

15. 作为实验室成员，我希望浏览实验室正式研究方向，以便形成整体认知。
16. 作为实验室成员，我希望搜索并按课题组、成员、资源类型和活跃状态筛选方向，以便快速定位相关领域。
17. 作为实验室成员，我希望阅读方向背景和范围说明，以便理解它解决什么问题以及不包含什么。
18. 作为实验室成员，我希望查看方向相关成员，以便寻找合作或咨询对象。
19. 作为实验室成员，我希望查看方向代表成果，以便了解实验室在该方向的积累。
20. 作为实验室成员，我希望查看方向公共资源，以便开始复用已有数据、代码或模型。
21. 作为新成员，我希望按顺序阅读方向学习入口，以便快速进入研究上下文。
22. 作为实验室成员，我希望查看与当前方向相关的其他方向及关联理由，以便发现跨方向联系。
23. 作为实验室成员，我希望查看方向最新动态，以便了解近期人员、项目和资源变化。
24. 作为 PI/Admin，我希望创建、编辑、合并、归档正式研究方向，以便维护规范目录。
25. 作为普通成员，我希望提交新增或修改研究方向的建议，以便贡献领域知识而不直接破坏正式结构。
26. 作为 PI/Admin，我希望从现有资源中选择并排序学习入口，以便避免复制资料和权限。
27. 作为 PI/Admin，我希望置顶或隐藏不适合作为方向动态的活动，以便保持页面有效信息密度。
28. 作为项目负责人，我希望将项目关联到多个研究方向，以便表达交叉研究。
29. 作为知识维护者，我希望方向关系记录关联理由、来源和修改历史，以便审计关系质量。
30. 作为实验室成员，我希望将成熟的研究对象关联到既有方向或建议创建正式方向，以便项目产出沉淀为实验室长期知识。

### Resources

31. 作为实验室成员，我希望在统一目录浏览数据、文档、代码、模型权重和 GPU，以便不再依赖口头询问。
32. 作为实验室成员，我希望按资源类型、研究方向、维护人和可见范围筛选资源，以便缩小查找范围。
33. 作为实验室成员，我希望理解资源用途、适用场景和限制，以便判断是否值得申请。
34. 作为实验室成员，我希望知道资源维护人，以便在资源过期或不可用时找到责任人。
35. 作为实验室成员，我希望看到资源的获取流程、前置条件和申请入口，以便采取下一步行动。
36. 作为已获权成员，我希望查看受限资源的内部地址，以便实际访问资源。
37. 作为未获权成员，我希望只能看到安全的目录信息和申请方式，以便系统不泄露敏感位置。
38. 作为数据使用者，我希望查看数据格式、规模、数据字典和使用限制，以便正确评估数据。
39. 作为代码使用者，我希望查看仓库地址、运行环境、许可证和主要入口，以便快速运行代码。
40. 作为模型使用者，我希望查看框架、模型版本、存储位置和运行要求，以便评估部署条件。
41. 作为 GPU 使用者，我希望查看机器或集群配置、维护人和登录说明，以便了解可用计算资源。
42. 作为资源维护人，我希望更新资源说明、版本状态和获取方式，以便目录保持有效。
43. 作为 PI/Admin，我希望管理资源类型、可见性和维护责任，以便落实实验室治理。
44. 作为项目成员，我希望把有权访问的公共资源关联到项目，以便在项目问答和任务中复用。
45. 作为安全负责人，我希望系统拒绝保存密码、令牌、SSH 私钥和云密钥，以便知识目录不成为凭据存储。

### AI Knowledge Assistant

46. 作为实验室成员，我希望询问“谁在研究某个主题”，以便获得相关成员及依据。
47. 作为实验室成员，我希望询问“实验室有哪些相关方向”，以便从自然语言进入知识地图。
48. 作为实验室成员，我希望询问“某项任务可以使用哪些资源”，以便发现数据、代码、模型和计算资源。
49. 作为实验室成员，我希望在答案中点击成员、方向和资源进入详情，以便连续探索。
50. 作为实验室成员，我希望从实体详情页带着当前上下文继续提问，以便减少重复说明。
51. 作为实验室成员，我希望答案区分已确认事实、来源内容和系统推断，以便判断可信度。
52. 作为实验室成员，我希望重要事实附带来源，以便核实答案。
53. 作为实验室成员，我希望 Assistant 在没有证据时明确说明不知道，以便避免虚构实验室知识。
54. 作为受限项目成员，我希望 Assistant 只使用我当前有权访问的项目内容，以便保护科研隐私。
55. 作为普通成员，我希望 Assistant 可以提出知识更新建议但不能直接修改正式实体，以便兼顾效率与治理。
56. 作为本地部署管理员，我希望使用本地模型时仍能完成全部知识问答，以便支持隔离网络环境。
57. 作为用户，我希望模型服务不可用时仍可浏览、搜索和人工维护知识，以便核心目录不依赖 AI。

### Governance and Migration

58. 作为 Admin，我希望现有账号、课题组、项目和研究资产自动迁移为初始知识数据，以便降低上线成本。
59. 作为 PI，我希望查看系统生成的成员、方向和资源关联候选，以便批量确认初始化结果。
60. 作为 PI，我希望同名冲突进入人工核对清单，以便系统不静默合并不同实体。
61. 作为审核者，我希望查看每项 AI 建议的目标、变更内容和依据，以便做出可靠决定。
62. 作为审核者，我希望批准或拒绝建议，并保留审核结果，以便追踪治理过程。
63. 作为审计者，我希望查看正式信息的创建者、修改者、来源和有效时间，以便解释知识如何形成。
64. 作为系统管理员，我希望重新执行失败的聚合任务不会产生重复关系或重复动态，以便安全恢复。
65. 作为资源负责人，我希望来源撤回后保留历史引用但不再用于新答案，以便兼顾可追溯性和现状准确性。
66. 作为 PI/Admin，我希望向课题组或研究方向委派 Knowledge Steward，以便知识治理不依赖单一 PI。
67. 作为 Knowledge Steward，我希望处理自己作用域内的建议和知识新鲜度待办，以便及时维护知识。
68. 作为建议提交者，我希望收到站内审核结果，以便知道建议是否生效及被拒绝的原因。
69. 作为成员，我希望关闭自动聚合的近期工作展示，以便在保持基础组织信息可见的同时控制派生活动曝光。

## Product Requirements

### People

- 成员目录必须只默认展示活跃成员，并提供归档成员的受控入口。
- 基础画像包含姓名、角色、课题组、简介、当前方向和咨询主题。
- 可咨询主题允许自由输入，但界面应优先推荐已有规范主题并引导关联至少一个正式 Research Direction；筛选使用正式方向和规范主题，不直接依赖未经归一化的自由文本。
- 历史方向关联必须记录开始时间、结束时间、来源和维护者。
- 代表成果由本人或 PI 从有权访问的研究资产及项目产出中选择。
- 近期工作由内部活动聚合生成，并逐条执行权限判断。
- 成员可以选择不展示自动聚合的近期工作；姓名、正式角色、课题组和经确认的当前研究方向属于实验室组织记录，不受该 opt-out 影响。
- 本人可以直接维护简介和咨询主题；本人接受 AI 对这些字段的建议后即可生效。PI/Admin 或获委派的 Knowledge Steward 负责其作用域内的正式方向关系。
- 当简介、咨询主题、代表成果或近期工作因未填写、opt-out 或权限裁剪而为空时，页面必须解释原因，并提供有权限用户可执行的补充、确认或申请访问入口，不展示无说明的空白区域。

### Research

- Research Direction 是独立于项目和临时研究对象的实验室级规范实体。
- 方向包含名称、摘要、背景、范围、状态、负责人和治理元数据。
- 方向与成员、项目、资源和代表成果建立显式关联，并保留时间和来源。
- 方向之间首版只支持“相关方向”，必须记录关联理由。
- Research 首页采用目录与轻量关系概览的混合布局。
- 学习入口引用现有资源并支持人工排序，不复制资源内容或权限。
- 成熟 ResearchObject 可以发起“关联既有方向”或“建议创建正式方向”，但只能通过 Suggestion 审核后形成正式关系或方向。
- 方向的代表成果、公共资源、学习入口和最新动态因尚未维护或权限裁剪而为空时，必须区分“暂无内容”“无权查看”和“等待确认”，并提供下一步入口。

### Resources

- ResearchAsset 继续作为统一资源治理载体，不建立平行资源体系。
- 所有资源共享名称、类型、用途、维护人、方向、可见性、获取方式、版本和更新时间。
- 数据、代码、模型权重和 GPU 使用类型专属元数据；未知类型仍保留通用展示能力。
- 获取方式只能保存说明、申请入口和受权限保护的地址，不得保存凭据。
- GPU 状态由维护人手工更新；系统不得暗示其为实时状态。
- 所有资源必须记录 `last_confirmed_at` 和下次复核时间；超过复核时间后显示“信息可能已过期”，但不自动撤回资源。
- 资源因无权限、尚未补充获取方式或已撤回而不可用时，详情页必须展示明确状态及申请、联系维护人或返回替代资源的入口。

### AI Knowledge Assistant

- 产品只提供一个 Assistant 体验。全局入口默认创建实验室范围对话；从项目页面进入时默认创建当前项目范围对话。现有项目问答作为统一 Assistant 的项目范围，不长期保留独立顶级入口。
- 每段对话创建时固定为实验室范围或指定项目范围；切换范围必须创建新对话并向用户解释，不能在同一会话中静默混合。
- Assistant 必须同时支持结构化实体检索和有权限资源内容的 RAG 检索。
- 权限裁剪必须发生在内容发送给 LLM 之前。
- 答案必须返回可展示的来源和实体引用，支持跳转详情页。
- 对无法验证的信息必须返回不确定或无答案状态。
- AI 建议写入审核队列，不能直接写入正式实体或关系。
- 使用本地模型时不得依赖外部联网服务。
- 没有命中、命中内容被权限裁剪、索引处理中或模型不可用必须使用不同的降级状态；每种状态都应提供可执行的下一步，而不是返回通用空答案。

### Notifications, Localization and Performance

- v1 提供站内审核待办、审核结果通知、知识过期提醒和维护人重新确认提醒；不建设邮件、IM 或移动推送系统。
- 所有用户可见字符串必须使用现有 i18n 机制，同时提供 en-US 和 zh-CN 文案。
- 目标规模内，结构化读取接口的服务端响应时间目标为 p95 小于 200ms，结构化写入接口为 p95 小于 500ms；Assistant 流式生成不适用该预算，但必须单独记录首 token 和完整响应时间。
- 关系概览必须使用分页和邻居数量上限，不允许一次加载完整实验室关系网络。

## Implementation Decisions

### Architecture

- 保持现有 React、FastAPI、PostgreSQL、Qdrant 和 LiteLLM 技术栈。
- PostgreSQL 是 People、Research、Resources、关系、审核和历史的权威数据源。
- Qdrant 只负责有权限资源正文的语义检索，不负责实体权威关系。
- 建立统一知识查询层，向浏览页面和 Assistant 提供一致的实体、关系、来源及可见性结果。
- 不引入图数据库，也不建立承载所有领域对象的万能 Entity 表。
- 结构化查询按 20–100 名活跃成员、最多 200 个正式方向和最多 50,000 项资源设计；列表、关系和活动必须分页，轻量关系概览必须限制展开深度与邻居数量。
- 单实例单实验室是 v1 的运行假设，而不是永久数据归属假设。新表的主键、唯一约束和服务接口必须记录未来增加 `lab_id` 所需的迁移点，但 v1 不提前实现多租户授权。

### Domain Modules

- **People Profile**：扩展现有用户和课题组成员体系，管理权威画像、方向历史、咨询主题和精选成果。
- **Research Direction**：管理正式方向、方向关系、学习入口、负责人和生命周期。
- **Resource Catalog**：扩展现有研究资产，管理类型专属元数据、维护责任和获取说明。
- **Knowledge Relation**：以明确的领域关联表维护成员、方向、项目、资源、成果和研究对象（ResearchObject）关系，记录来源与有效时间。ResearchObject 与 ResearchDirection 的关系类型须可扩展，以容纳后续 hypothesis/contradiction/gap 子类而不改 schema。
- **Knowledge Suggestion**：统一承载人工或 AI 提出的变更建议、依据与审核结果。
- **Activity Projection**：将现有项目活动、资源发布和研究产物投影为近期工作与方向动态，保证幂等。
- **Knowledge Query**：执行结构化搜索、关系展开、权限裁剪和来源组装。
- **Assistant Retrieval**：编排结构化实体结果与现有 RAG 结果，并输出可引用、可导航的回答上下文。
- **Assistant Experience**：向全局和项目入口提供同一个会话体验，在创建会话时固定实验室或项目范围；底层可以分别复用知识查询和现有项目问答编排。
- **Knowledge Operations**：提供站内待办、审核结果、知识新鲜度提醒、完整度和仅本地聚合的采用度指标。

### Governance

- PI/Admin 创建、合并和归档正式研究方向。
- 普通成员可以提交方向和关系建议，但不能直接修改正式知识地图。
- PI/Admin 可以向指定 Research Group 或 Research Direction 委派和撤销 Knowledge Steward，不新增全局系统角色。
- Knowledge Steward 可以审核其作用域内的成员—方向关系、方向说明、学习入口、相关方向、资源元数据、资源—方向关系和知识新鲜度确认。
- 创建、合并、归档正式方向，跨课题组关系治理，资源权限与分类，访问授权以及 Steward 委派仍只允许 PI/Admin 执行。
- 成员本人直接维护简介和咨询主题；本人可以审核 AI 对这些字段的建议。PI/Admin 或相应 Knowledge Steward 维护正式方向关系。
- 资源维护人维护说明和版本；PI/Admin 管理分类、可见性和维护责任。
- AI 建议必须由本人、PI、Admin 或相应 Knowledge Steward 按目标字段权限审核。
- v1 不采用“超时默认接受”；未处理建议保持待审状态。站内待办必须显示等待时长，并允许 PI/Admin 重新委派长期未处理的队列。

### Visibility and Privacy

- People 基础画像、正式 Research 方向及两者关系对实验室成员可见。
- 资源标题、类型、用途、维护人和申请方式默认可发现，但敏感地址和内容按权限显示。
- 项目、成果、近期工作、方向动态和 Assistant 答案逐条继承来源权限。
- 查询时权限判断是最终权威。派生记录只保存来源引用和安全摘要，不持久化可绕过原始权限的受限正文。
- 用户失去访问权后，权限变更必须触发相关缓存失效；后续实体查询、聚合结果和 Assistant 检索必须立即停止返回受限内容。Qdrant 命中结果在返回或发送给 LLM 前仍须按来源逐项重新鉴权，不能信任历史索引时的权限快照。
- 缓存键、最大有效时间、权限变更事件和向量结果二次鉴权方案必须在阶段 0 通过技术与安全评审，且有撤权回归测试后才能进入阶段 1。
- LLM 不得接收当前用户无权查看的资源正文或受限实体字段。

### Lifecycle and Failure Handling

- 人员离开、方向停止和资源下线采用归档或撤回，保留历史关系。
- 来源撤回后保留历史引用和状态提示，但不得用于新的事实依据。
- 自动聚合失败时保留已有画像和动态，记录可重试错误，不写入部分结果。
- 聚合与迁移操作必须幂等。
- 同名成员、方向或资源冲突进入人工核对，不进行静默合并。
- LLM 或向量检索不可用时，结构化浏览、搜索和人工维护保持可用。
- 关系目标归档后保留关系历史，并在展示中明确目标状态。
- 成员画像、正式方向和资源均记录上次确认时间与复核期限；过期只改变新鲜度状态，不自动改变事实、可见性或访问权限。
- v1 保留带有效时间的历史记录，但不提供任意时间点的 as-of 查询 UI 或公共 API；后续版本可以在不改变历史数据语义的前提下增加该能力。

### Migration

- 现有 User 迁移为 People 基础记录，不创建第二套账号。
- 现有 ResearchGroup 和成员关系继续作为实验室内部课题组体系。
- 现有项目和项目成员关系用于生成待确认的方向与成员关联候选。
- 现有 ResearchAsset 原地扩展为资源目录，不复制资产和权限。
- 现有 ResearchObject 保持其会话研究产物含义，不自动升级为正式 Research Direction；成熟的 ResearchObject 可由用户发起或 AI 建议"关联既有方向"或"建议创建正式方向"，统一进入审核队列。
- 初始化过程中由 PI/Admin 创建或确认正式方向，再批量审核成员、项目和资源关联候选。

### Delivery Phases

1. **阶段 0：共同基础与需求基线**
   - 建立 Research Direction、Knowledge Relation、Suggestion、来源、有效时间和历史机制。
   - 从真实成员收集并冻结 30 个问题基准集。
   - 完成现有数据盘点、迁移试运行、权限威胁模型、缓存/索引撤权方案和安全基线测试。
   - 退出条件：领域边界与安全方案通过技术评审；基准问题覆盖找人、找方向、找资源和交叉探索；试迁移能够对账且冲突进入人工清单。
2. **阶段 1：Resources**
   - 交付统一资源目录、类型专属字段、维护人、获取方式、新鲜度及基础方向关联。
   - 退出条件：关键资源可搜索；原有权限、发布、访问申请和项目引用无回归；用户可以理解获取路径；无内容、无权限、已撤回和信息过期状态均有可执行下一步。
3. **阶段 2：People + Research**
   - 交付成员与方向目录、详情、Steward 治理、历史、ResearchObject 毕业建议和轻量关系概览。
   - 同期交付最小 Activity Projection，只投影资源发布、项目活动和明确研究产物。
   - 退出条件：活跃成员基础画像和正式方向达到完整度门槛；近期工作与方向动态均可追溯；权限裁剪和 opt-out 后页面仍提供正确的空状态。
4. **阶段 3：统一 AI Knowledge Assistant**
   - 交付实验室范围与项目范围的统一入口、跨实体检索、引用、实体跳转和详情页上下文提问。
   - 退出条件：冻结的 30 问题基准集达到 90% 可回答、80% 事实正确和零权限泄露；实验室与项目范围均通过回归；切换范围不会静默混合；模型不可用时目录能力不受影响。
5. **阶段 4：持续维护与运营**
   - 上线 AI 更新建议、Steward 待办、站内通知、新鲜度提醒、完整度看板和本地采用度指标。
   - 退出条件：建议审核、长期待办重新委派、过期提醒和隐私保护的本地指标可运行；形成 v1 复盘记录，并明确是否将 Discovery Loop 集成作为 v1.5/v2 主题。

每个阶段必须可独立演示、测试和回退。后续阶段不能成为前面目录与人工维护能力可用的前置条件。

## Testing Decisions

### 测试原则

- 测试外部可观察行为，不锁定内部实现、SQL 形态或模型具体措辞。
- 权限、迁移和历史完整性属于发布阻断测试。
- AI 测试使用固定实验室数据集评估实体命中、来源充分性、无答案行为和权限隔离。
- 聚合与迁移必须覆盖重复执行、部分失败和恢复场景。

### 模块测试

- **People Profile**：编辑权限、历史方向、精选成果、近期工作权限裁剪和建议审核。
- **Research Direction**：创建、编辑、合并、归档、相关方向、学习入口、ResearchObject 毕业建议和动态治理。
- **Resource Catalog**：类型元数据、维护人、获取信息、新鲜度、访问申请、版本和现有资产兼容。
- **Knowledge Relation**：有效时间、来源、ResearchObject 端点、归档目标、重复关系和权限。
- **Knowledge Suggestion**：提交、批准、拒绝、本人审核、Steward 作用域、重复处理和无权限审核。
- **Activity Projection**：幂等刷新、来源撤回、失败重试和不同请求者的可见结果。
- **Knowledge Query**：结构化搜索、关系展开、权限裁剪、撤权后缓存失效、向量结果二次鉴权和稳定分页。
- **Assistant Retrieval**：结构化与 RAG 合并、实验室/项目固定范围、引用、无答案、索引处理中、模型不可用和零越权。
- **Knowledge Operations**：站内待办、审核结果、新鲜度提醒、重新委派和不记录正文的本地采用度指标。
- **Migration**：账号、课题组、项目、资产、权限和历史关联的前后对账。

### 前端关键旅程

- 从成员目录筛选并进入成员详情，再跳转相关方向与负责资源。
- 从 Research 目录进入方向详情，使用学习入口和相关方向继续探索。
- 从 Resources 找到资源，理解获取条件并发起已有访问申请流程。
- 从全局入口创建实验室范围 Assistant 对话，通过答案中的实体链接进入详情，再带实体上下文继续提问。
- 从项目页进入同一个 Assistant 体验并创建项目范围对话；切换到实验室范围时创建新对话且不混合原项目上下文。
- 审核者处理 AI 建议，批准后在浏览和问答中看到一致结果。
- 用户在无内容、无权限、opt-out、信息过期、索引处理中和模型不可用状态下都能理解原因并执行正确下一步。

### 现有测试先例

- 继续沿用项目成员、课题组成员和角色权限测试模式。
- 继续沿用研究资产公开/私密、访问申请、项目引用和撤回测试模式。
- 继续沿用项目 RAG、引用和编排运行的固定数据与权限测试模式。
- 继续沿用研究对象关系的重复关系、证据和归档测试思路，但不混淆临时研究对象与正式方向。

## Out of Scope

- 多实验室租户和跨实验室知识共享。
- 独立图数据库、完整知识图谱编辑器、自由拖拽节点和复杂关系本体。
- AI 自动创建或直接修改正式成员画像、研究方向和资源关系。
- ORCID、Google Scholar、GitHub、模型仓库或外部新闻的自动同步。
- 引用量、影响因子和外部学术排名。
- 个性化课程生成和自动领域新闻摘要。
- GPU 实时监控、调度、配额、作业提交和自动账号开通。
- 密码、访问令牌、SSH 私钥、云密钥或其他秘密信息管理。
- 代替现有权限系统执行资源审批或授权。
- 将普通聊天自动认定为正式成果。
- 跨无权限项目汇总或推断敏感科研信息。
- AI 建议超时自动接受。
- 邮件、IM、移动推送等外部通知渠道。
- 任意时间点的 as-of 历史查询 UI 或公共 API。

## Risks and Mitigations

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 方向命名和边界不稳定 | 重复实体、关系混乱 | PI/Admin 治理；成员提交建议；支持合并与归档 |
| 自动聚合产生噪声 | 画像和动态失去可信度 | 只使用明确内部事件；允许隐藏；不将聊天自动认定为成果 |
| People 页面泄露项目活动 | 严重隐私问题 | 每条派生内容动态权限裁剪；越权测试阻断发布 |
| Assistant 混合检索泄露受限正文 | 严重隐私问题 | 在发送给 LLM 前裁剪；使用固定攻击与回归数据集 |
| 现有 ResearchObject 与正式方向概念混淆 | 模型和 UI 难以维护 | 保持独立领域实体，通过显式关联连接 |
| 资源类型字段过度设计 | 开发慢且难适配未知资源 | 公共字段稳定；类型元数据渐进增加；保留通用展示 |
| AI 建议过多造成审核负担 | 建议队列无人处理 | 仅高置信度、可解释建议入队；支持批量审核和频率限制 |
| PI 或 Steward 不活跃 | 审核和知识确认长期停滞 | 作用域委派；待办老化；PI/Admin 重新委派；不使用静默自动接受 |
| 权限撤销后缓存或向量结果仍可命中 | 严重隐私问题 | 查询时逐源鉴权；权限事件失效缓存；阶段 0 完成威胁建模和撤权测试 |
| 权限裁剪导致详情页接近空白 | 用户误以为系统没有知识 | 区分无内容、无权限和待确认；提供申请访问、补充信息或联系维护人入口 |
| 知识条目过期 | 成员依据陈旧信息行动 | 记录确认与复核时间；显示过期状态；站内提醒维护人和 Steward |
| 初始化工作量超预期 | 上线延迟 | 自动迁移确定性数据；生成候选；按关键成员、方向和资源优先补齐 |
| 单实例单实验室假设固化进唯一约束和接口 | 未来多实验室迁移成本高 | v1 记录需增加 lab 维度的表和约束；服务边界避免依赖全局唯一业务名称 |

## Further Notes

### 关键产品判断

- 本版本的核心不是增加四个导航页面，而是让四个入口共享同一套稳定、受治理、可追溯的知识关系。
- Research Direction 不应被项目或会话产物替代；它是实验室长期知识地图的主干。
- Resources 是现有能力复用度最高的部分，应扩展而非重建。
- People 自动更新必须以可追溯内部事件为基础；AI 的角色是建议，不是权威写入。
- Assistant 的差异化价值是回答后能够继续浏览实体，以及浏览后能够带上下文继续提问。

### 评审决策记录

- 2026-08-09（Q1：与 Discovery Loop 的关系，已拍板）：采纳"知识基础层"定位。Research Direction 承载长期研究领域与上下文；hypothesis、contradiction、gap 将作为过程型 ResearchObject；两者显式关系连接；成熟 ResearchObject 可发起"关联既有方向"或"建议创建正式方向"并进入审核队列；v1 只交付关联与建议入口，不扩入新的 Discovery Loop 能力；本周期不并行推进新的 Discovery Loop 功能；v1 验收（基准问题集评测通过）即触发下一版本 Discovery Loop 集成评估。详见"与 Discovery Loop 的关系"一节。
- 2026-08-09（Q2：治理瓶颈，已拍板）：采用作用域化 Knowledge Steward；成员自助维护简介和咨询主题；使用站内待办和重新委派，不采用超时自动接受；高风险治理仍由 PI/Admin 承担。
- 2026-08-09（Q3：问答入口，已拍板）：产品上只有一个 Assistant 体验；全局入口创建实验室范围对话，项目入口创建项目范围对话；对话范围固定，切换范围新建对话；后端渐进复用现有项目问答运行时。
- 2026-08-09（Q4：交付顺序，已拍板）：阶段顺序调整为共同基础与需求基线 → Resources → People + Research（含最小 Activity Projection）→ 统一 Assistant → 持续维护与运营；每阶段使用明确退出条件，Assistant 质量门槛不得推迟到阶段 4。

### 需要评审批准的范围结论

- 采用单实例单实验室模型，Research Group 表示内部课题组。
- 采用共同基础 + 分阶段纵向切片的交付方式。
- Lab Knowledge OS 是 Discovery Loop 的知识基础层，本周期不并行扩展新的 Discovery Loop 能力；v1 验收触发下一版本集成复盘。
- 采用作用域化 Knowledge Steward，不采用 AI 建议超时默认接受。
- 只提供一个 Assistant 体验，通过实验室或项目固定会话范围复用不同检索能力。
- 首版 Research 只维护“相关方向 + 关联理由”。
- GPU 首版仅做知识目录，不做实时基础设施能力。
- 首版不依赖任何外部学术数据源或联网搜索。
- 阶段顺序为共同基础与需求基线 → Resources → People + Research → 统一 Assistant → 持续维护与运营。
- 首轮使用本 PRD 中定义的覆盖率、30 问题基准集和零权限泄露门槛验收。
